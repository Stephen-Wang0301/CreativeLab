# 版本、服务器同步与数据恢复

工作目录固定使用 `004CreativeLab`。修改、部署和保存版本均在这个目录内进行，无需关闭 Codex 或重新命名文件夹。

## 对话操作编号 1–11

编号用于协作对话，不再使用 BAT 菜单。可以直接说“执行 5，更新服务器测试，不存版”。只讨论某项操作不代表要求执行它。

| 编号 | 操作 | 范围与结果 |
| --- | --- | --- |
| 1 | 保留服务器方案草稿 | 草稿已保存，不发布、不部署、不存 Git |
| 2 | 发布服务器方案草稿 | 暂停新报名、发布下一采集版本、恢复此前的招募状态；已有参与者留在原版本 |
| 3 | 修改电脑代码并预览 | 不创建 Git 提交、不上传 GitHub、不部署服务器 |
| 4 | 保存代码阶段版本 | 创建 Git 提交并上传 GitHub；服务器不变 |
| 5 | 部署当前代码供测试 | 更新服务器，不创建 Git 提交、不上传 GitHub |
| 6 | 保存代码版本并部署 | 创建提交、上传 GitHub，再部署同一提交 |
| 7 | 恢复指定 Git 代码版本 | 指明提交及目标：电脑、服务器或两者；不隐式恢复数据 |
| 8 | 下载服务器完整私有备份 | 所有版本、普通/快速演练数据、草稿、评分、密钥及迁移凭据；核对 SHA-256 |
| 9 | 取回服务器代码比较、合并 | 先下载到私有对照目录，不直接覆盖电脑文件 |
| 10 | 按部署编号回退服务器代码 | 包括未存入 Git 的测试部署；保留当前实验数据 |
| 11 | 恢复特定方案或实验数据 | 明确恢复对象、快照时间和范围，不静默覆盖较新的作答 |

可组合“2＋6”。新代码与新方案同时发布时，先验证兼容，再安排部署与发布顺序，保持原招募状态。旧 Git 版本或部署恢复前也要检查它能否读取当前数据库，保留尚未存版的电脑改动和后续 Git 历史。涉及字段、数据库、依赖或机器配置变化时，先准备兼容或迁移；不能只上传代码文件。

## 三件事分别控制

| 操作 | 结果 | 是否产生 Git 提交 |
| --- | --- | --- |
| 修改本机代码 | 留在工作区，随时继续调整 | 否 |
| 更新测试网站 | 上传当前代码，预检、备份并短暂重启实验服务 | 否 |
| 保存阶段版本 | 按你给出的说明创建一个本地提交 | 是，仅在你决定时 |
| 上传 GitHub | 推送已经保存的提交 | 不创建新提交 |

你可以直接告诉协作助手“更新测试网站，暂不存版”“把这一阶段保存，说明是……”或“把已保存版本上传 GitHub”。阶段由你决定，不按次数、日期或每次聊天自动划分。

旧 BAT 菜单及其 PowerShell 菜单脚本已移除。协作助手根据上述对话指令调用底层工具；也可在项目目录运行以下命令。使用已配置 Python 3.12 的 `skillcourse` 环境。

```powershell
python deployment/manage.py status
python deployment/manage.py check
python deployment/manage.py deploy --working-tree
python deployment/manage.py save -m "预试流程确认，等待下一轮测试"
python deployment/manage.py publish
```

保存时显示改动并要求输入 `SAVE`；推送时要求输入 `PUBLISH`。发布到 GitHub 不会部署到网站。命令中的 `--confirm` 仅供已经得到你明确确认的助手执行，不能作为默认自动选项。

## 隐私边界

- 根 `README.md` 是私人使用说明，可以保留实际网址、邀请口令和后台密钥。GitHub 展示的是 `.github/README.md`。
- `data/` 保存数据库、方案草稿、发布材料、密钥和受试者记录；以服务器上的副本为准。
- `private/server.json` 保存本机部署连接参数；`.runtime/deploy_ed25519` 是专用 SSH 私钥，服务器仅登记其公钥。GitHub 凭据保留在本机凭据管理器，不传给服务器。
- `.runtime/`、`backups/`、`logs/`、平台运行环境、生成清单、实际 systemd/隧道配置均不上传 GitHub。
- Git 忽略规则加可公开路径检查；提交前检查暂存内容，推送前还检查 Git 历史。检查不会显示匹配的密码。扫描只能识别已知私密值和常见令牌格式，保存前仍需审阅改动。

Git 的忽略规则不影响已经被跟踪的文件，因此还需检查历史内容，不能只看当前目录是否删除了敏感文件。参见 [Git 忽略规则](https://git-scm.com/docs/gitignore) 与 [GitHub 敏感数据处理说明](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)。

## 代码同步到服务器

首次配置由维护人员复制 `server.example.json` 到 `private/server.json`，设置并验证 SSH 密钥和主机指纹。实验服务的启停需要授权；此项目仅为专用部署账号配置对实验服务 `start/stop` 的有限授权，不授权其他服务或任意 sudo 命令。

部署工具先比较服务器代码哈希与本机保存的服务器基线，发现外部改动就停止。下载服务器代码到独立的私有目录进行比较：

```powershell
python deployment/manage.py server-status
python deployment/manage.py fetch-code
```

核对并合并改动后，明确接受当前服务器基线：

```powershell
python deployment/manage.py server-status --accept-baseline
```

部署支持两种来源：

```powershell
python deployment/manage.py deploy --working-tree
python deployment/manage.py deploy --ref main
```

第一种包含未提交的当前代码，供反复测试；第二种使用指定 Git 提交、分支或标签的已保存代码。两者都会记录来源、文件哈希、部署时间和回退编号，不把临时部署记录变成 Git 阶段提交。

实际流程：独立目录启动预检 → 生成服务器整站备份 → 保存部署前后的源代码 → 暂停实验服务 → 仅替换允许的源代码文件 → 启动服务 → 检查应用、受试者页、后台页及公网 HTTPS。Cloudflare 隧道及其他业务服务不随代码部署重启。更新有短暂停机，测试/招募期间应安排在无人作答时执行。

同步不上传本机 `data`，不覆盖线上方案、作答、密码和 Cloudflare 令牌。第三方依赖和机器配置也不自动替换；以后如改动 `requirements.txt`，需先单独准备匹配的服务器依赖，再部署。

## Git 回退与服务器回退

查看已保存的阶段：

```powershell
git log --oneline --decorate
```

试运行某个旧提交可用 `deploy --ref 提交编号`。无需先改本机文件，也无需删除后续历史。需要把旧代码作为新的开发起点时，先保留当前工作区，再由维护人员选择分支或反向提交；不要直接强制重置含未保存改动的工作区。

每次部署返回 `release_id` 和 `rollback_before_this_deploy`。根据编号恢复部署后的代码，或恢复那次部署之前的代码：

```powershell
python deployment/manage.py rollback 部署编号
python deployment/manage.py rollback before-部署编号
```

回退会先备份，再恢复代码并验证服务。它不把数据库回到过去，因此不会为了回退界面而删除后来新增的作答。未来涉及不兼容数据库迁移的版本，需另行设计迁移与恢复方案，不能只依赖代码回退。

## 后台内容与数据备份

后台“方案与招募”的编辑保存到服务器数据库，刷新后保留；后台“保存为新版本”管理的是实验材料版本，与这里的 Git 代码版本各自独立。

展示版本为 **阶段.内容.功能**，当前 `0.1.1`：第一位 0 为预试、1 为正式；第二位为作答内容与流程版本；第三位为功能补丁。功能维护不增加第二位，也不发布服务器尚存的方案草稿。明确发布新内容时进入 `0.2.1` 等版本。每一位按整数比较，`0.10.1` 在 `0.9.1` 后。Git 提交编号仍独立于展示版本。

功能补丁共用内容批次：`0.1.1`、`0.1.2` 的材料相同，因此继续在 `batches/pilot/v0.1` 下收集、共同筛选，不新开空批次。参与编号、原冻结协议和身份文件不变，`releases/0.1.1.json` 另记功能清单。新参与者的 `enrolled_release` 和操作时的 `last_release` 记录实际功能版本；历史未标记数据按原内容版的 `.0` 保留来源。后续功能更新需明确维护 `study/catalog.py` 的功能序号，不因每次保存草稿自动增长。

统一 SQLite 为全部批次提供索引，每位参与者固定关联报名时的版本。数据库限制已发布方案被改写、参与者被移到别的版本或被删除。文件另按批次独立归档：

```text
data/
  _system/study.sqlite3
  batches/
    pilot/v0.1/
      batch.json                     阶段、版本、批次标识
      protocol.json                  冻结的已发布方案，禁止以不同内容覆盖
      participants/S0-V0001-P000001/  第 0 阶段、第 1 版、第 1 位参与者
    pilot/v0.2/                      下一版本的独立批次
    formal/v1.1/                     正式阶段首个版本
  quick-demo/                        独立演练数据；其参与者编号另加 Q- 前缀
```

例如 `S0-V0002-P000003` 对应预试 0.2 的第 3 位参与者。参与者编号在批次内按事务分配，不重复使用。原 `P-...` 技术编号、恢复码、会话、稿件和事件记录保留，新编号作为便于管理的别名，两种编号均可恢复进度。旧的 `data/pilot/P-...` 目录作为迁移留存保留，当前导出及新文件使用按版本归档的目录。

右上角只列出真实已发布版本，不再重复列“当前版本 #1”和“示例材料”。选中哪个版本，概览、参与者、原始 ZIP、分析和评分就使用哪个版本。邀请链接始终指向当前发布版本；筛选历史数据不会改变招募版本。历史参与者继续原方案，本版本招募上限独立计算。

随时下载整个站点，包括两套数据、材料版本、草稿、评分、密钥和迁移凭据：

```powershell
python deployment/manage.py backup
```

文件落在本机私有 `backups/`，下载后验证 SHA-256。它适合迁移到下一台服务器或恢复到本机。GitHub 上的代码和私有备份合起来才是完整恢复路径。后续代码保存和数据备份各自按需执行，没有配置按日自动任务。

## 换电脑或服务器

克隆 GitHub 仓库后运行 `python deployment/bootstrap.py` 安装固定依赖并启用检查钩子。下载最新私有整站备份，按服务器操作说明恢复完整 `data` 和私有凭据。新服务器重新安装对应平台的 Python、cloudflared 和 systemd 服务，再在私有配置中更新连接目标。现有站点可用前保留旧服务器副本。

服务器 SSH 登录密码不存入部署配置。专用私钥丢失时，可用原来的 SSH 登录方式重新配置公钥。撤销专用同步通路时，仅从服务器 `~/.ssh/authorized_keys` 移除注释为 `creative-study-deploy` 的公钥，并移除为实验服务添加的 sudoers 文件；保留其他人的密钥和权限。

## 个人邀请、重复参与与任务恢复

运行概览“生成新的个人邀请”为当前内容版本预留参与编号，只显示 `S0-V0001-P000021` 一种编号。实际链接含长随机标识和签名，不能只发送参与编号作为通行证。旧短标签仅作历史证据保留，旧链接仍有效。后台和受试者重开都通过同一个事务计数器分号，唯一约束防止重复，空缺不回收。

通用邀请可以发给首次参与、各自使用浏览器的多位测试者。已有浏览器会话继续原记录，不识别真实个人；共用电脑或再次体验请用不同个人邀请。个人邀请一份绑定一次参与；已报名者保留原版本，未使用的旧版邀请在内容切换后不能用于旧版新报名。

“待使用的个人邀请”每页十条。第一次报名成功、记录写入数据库后自动隐藏该邀请，不必等到全部答完；隐藏不会删除或作废链接。参与者详情“查看/复制继续链接”不触发人工恢复，不改变计时、作答或分组。

受试者点击“暂停 / ESC”或按 ESC，请求保存当前输入并由服务器冻结剩余时间。模糊遮罩下不能查看或操作内容，刷新及断线重连仍保持暂停；直接离开网页不会自动暂停。继续实验恢复同一步骤、分组和余时；“存档并退出”保持暂停，显示可关闭页面，并提供继续链接，不记录为主动退出。

预试“我要从头开始”须在二次确认中完整等待十秒，服务器也校验等待时间。确认后旧记录以 `restarted` 状态封存，全部答案、稿件、分组和事件保留，新任务领取独立编号及个人链接、重新同意知情说明。记录以 `restart_to` / `restart_from` 关联。正式阶段暂时禁用自行重开，需要研究人员发新邀请。

人工“恢复任务”用于真实中断/超时，需要原因和最新记录序号，并记录快照及干预。已自行暂停者直接用继续链接，无需人工恢复。已完成、主动退出或已重开的记录均不重新打开。`pause_count`、`pause_seconds`、逐次暂停记录及阶段事件的 `effective_seconds`、`recovery_count` 和重开关系供分析时核查；`pause_seconds` 是已结束的暂停累计，正在暂停的起点在响应状态中另存。重开旧记录不进入盲评资格。原始 ZIP 不包含访问链接；完整私有备份保留邀请、发号器和签名密钥。

新增暂停/封存状态后，回退至不理解这些状态的旧代码会被部署工具拦截。需准备兼容代码，不能通过删数据或静默恢复旧数据库解决。

## 页面响应与性能检查

页卡切换使用一次 dashboard 请求读取一致数据，概览等页面不再重复传输完整材料。已访问的只读页面可先显示短期缓存，再刷新；修改操作会清空缓存。界面立即显示加载反馈，迟到的旧请求不能覆盖新选中的页面。数据库确认前不会假装提交成功，计时和实验随机分组规则没有因性能优化而改变。响应带 `Server-Timing`，可区分服务器处理耗时与网络耗时。
